## 1. 서비스 정의

### 누구의 어떤 문제인가 [제안]

대표 장면: 19:30에 가족을 태우기로 했는데 19:10에 도착해 주차한 운전자.

- **쉬고 싶어도 쉬지 못한다.** 눈을 감으면 시간을 놓치거나 동승자가 온 걸 모를까 봐 시계와 휴대폰을 계속 확인한다.
- **차가 쉬기 좋은 상태가 아니다.** 운전 자세 그대로이고, 실내 조명과 바람 소리도 운전할 때 설정 그대로다.
- **휴대폰 알람은 상황을 모른다.** 동승자가 일찍 와도 알람은 그대로 울리고, 차를 움직여도 휴식 소리는 계속 난다.

### 사용 전후

| 사용 전 | 사용 후 |
| --- | --- |
| 시계를 보며 기다린다 | 끝나는 시각을 앱에 맡기고 눈을 감는다 |
| 운전 자세, 운전용 조명·바람 그대로 쉰다 | 시작하면 등받이가 젖혀지고, 무드등이 낮아지고, 바람이 줄고, 고른 온도로 맞춰진다 |
| 동승자가 왔는지 계속 살핀다 | 조수석 문이 열리면 앱이 휴식을 끝내고 차를 원래대로 돌린다 |
| 알람이 갑자기 울린다 | 끝나기 전에 소리가 서서히 줄고 안내음·음성으로 알린다 (오디오를 쓸 수 있을 때) |

### 차량이라서 가능한 가치

- **쉬어도 되는 상황인지 차가 안다.** 주차(P 기어)이고 주행 제한이 없을 때만 시작한다.
- **차가 쉬는 환경을 만든다.** 등받이, 무드등, 바람, 온도를 휴식에 맞게 바꾸고 끝나면 되돌린다. 휴대폰으로는 할 수 없다.
- **동승자 도착과 출발을 차가 안다.** 조수석 문이 열리거나 차를 움직이면 바로 끝낸다.

### 기존 프로토에 부족했던 점 (커밋 `db43cda` 코드 기준)

1. **휴식 방식을 고를 수 없다.** 빗소리 1종을 고정 음량(0.6)으로만 틀고, 끄거나 크기를 바꿀 수 없다.
2. **차를 휴식에 맞게 바꾸지 않는다.** 앰비언트 밝기를 읽어 앱 화면 밝기에만 반영했다. 시트·조명·공조는 건드리지 않았다.
3. **끝이 갑작스럽다.** 예정 시각에도 소리를 바로 끊고 화면 글자만 바뀐다. 정상 종료와 갑작스러운 중단이 같은 방식이다.
4. **끝난 뒤 흐름이 없다.** 종료 이유만 보여 주고, 다시 쉬는 흐름이나 설정 기억이 없다.
5. **시작 조건을 이해하기 어렵다.** 문 상태가 "확인 중"이면 사용자가 문을 한 번 열었다 닫아야 했다(프로토 README).
6. **잠깐의 다른 소리에도 휴식이 끝난다.** 오디오 포커스를 잠시만 잃어도 휴식 전체를 종료한다.

### 반복해서 쓸 이유 [제안]

- 픽업 대기는 같은 사람에게 반복해서 생긴다(학원·역·퇴근 픽업 등). 시장 규모·재사용률 수치는 근거가 없어 적지 않는다.
- 마지막 휴식 방식과 차량 연동 선택을 기억해, 다음에는 **픽업 시각 확인 → 시작** 두 번 조작으로 시작한다.
- **끝을 믿을 수 있어야 다시 쓴다.** 예정 시각, 동승자 도착, 차 움직임에 맞게 끝나고 차가 원래대로 돌아오는 것이 핵심 신뢰 요소다.

| 안내를 닫는다 | 준비 화면으로 간다. 이후 실행부터는 나오지 않는다 |

### 2-2. 휴식 준비

| 사용자 행동 | 앱 반응 |
| --- | --- |
| 준비 화면을 본다 | 시작 조건 3개를 체크로 보여 준다: **주차됨**(P 기어 + 주행 제한 없음), **조수석 문 닫힘**, **쉴 시간 충분**. 안 된 조건은 이유를 문장으로 쓴다. 문 상태가 미지원·확인 중·오류여도 시작할 수 없고 이유를 쓴다 |
| 픽업 시각을 정한다 | 처음 값은 지금부터 20분 뒤를 5분 단위로 올린 시각. **−5분 / +5분**으로 바꾼다. "휴식 종료 19:28 (픽업 2분 전) · 18분 쉴 수 있어요"를 보여 준다. 쉴 시간이 부족하거나 지난 시각이면 **[지금 기준으로 다시 설정]**을 보여 주고, 누르면 지금 기준 처음 값으로 한 번에 바꾼다. 누를 때만 바꾸고 저장·시작은 하지 않는다(STEP 35) |
| 휴식 방식을 고른다 | 휴식 소리 **켬 / 조용히**(휴식 소리만 끔), 소리 크기 3단계 |
| 차량 연동을 고른다 | **편한 자세**(운전석 등받이), **무드등**, **바람 줄이기**, **온도 맞추기**(목표 온도 선택) 각각 켬/끔. 차가 지원하지 않는 항목은 "이 차에서 지원하지 않아요"로 표시하고 끈다. 마지막 선택과 목표 온도가 기본값이다 |
| 시작을 누른다 | 시작 조건이 모두 맞을 때만 눌린다. 누르면 휴식 화면으로 가고, 켠 차량 연동을 적용한다(6장). 차량 연동이 실패해도 휴식은 계속한다. 이전 휴식의 기록이 정리되지 않은 항목은 이번에 바꾸지 않는다(6-1) |

- 휴식 종료 시각 = 픽업 시각 − 준비 여유(초기 검증값 2분).
- 종료 시각까지 3분 이상(초기 검증값) 남아야 시작할 수 있다. 마지막 60초(초기 검증값)는 종료 예고 구간이다. 화면 어둡게 전환 10초도 초기 검증값이다.

### 2-3. 휴식 중

| 사용자 행동 | 앱 반응 |
| --- | --- |
| 아무것도 하지 않는다 | 10초 뒤 화면을 아주 어둡게 하고 남은 시간만 흐리게 남긴다. 휴식 소리를 반복 재생한다(켬일 때) |
| 화면을 한 번 누른다 | 10초 동안 밝아지며 **소리 크기**, **휴식 소리 켬/끔**, **휴식 끝내기**와 차량 연동 상태(적용 확인 / 확인 못 함 / 바꾸지 않음)를 보여 준다 |
| 차 설정(등받이·조명·바람·온도)을 직접 바꾼다 | 그 항목은 사용자 선택으로 보고 더 건드리지 않으며, 종료 때도 되돌리지 않는다(6-1) |
| 종료 60초 전이 된다 | 휴식 소리를 줄이기 시작해 종료 시각에 0이 되게 한다 |

### 2-4. 종료와 복귀

| 종류 | 원인 | 앱 반응 |
| --- | --- | --- |
| **정상 종료** | 종료 시각 도달 | 휴식 소리는 이미 0이 되어 멈춘다. 쓰기 직전 확인(6-1)을 거쳐 조명·공조·시트를 되돌린다. 오디오 포커스를 얻으면 안내음 1회와 음성 "픽업 2분 전이에요"를 낸다. 화면을 밝히고 종료 화면을 보여 준다 |
| **갑작스러운 중단** | 조수석 문 열림, P 이탈·주행 제한, 문 신호 끊김, 오디오 영구 상실, 다른 앱으로 이탈, 시동 꺼짐 | 휴식 소리를 바로 멈춘다. 안내음·음성은 내지 않는다. 쓰기 조건이 맞으면 차량 연동을 되돌린다. **주행 전환이면 시트 이동을 멈추고 모든 복원을 보류한다**(6-1). 화면을 밝히고 중단 이유를 보여 준다 |
| **직접 종료** | "휴식 끝내기" | 휴식 소리를 바로 멈추고, 쓰기 조건이 맞으면 차량 연동을 되돌린 뒤 종료 화면을 보여 준다 |

종료 화면에는 **종료 이유, 종료 시각, 차량 연동 복원 결과, [다시 쉬기]**를 둔다. 정상 종료와 중단은 제목 문구로 구분한다. 복원 결과는 항목별로 6-1의 상태(원래대로 확인 / 직접 바꾸셔서 그대로 둠 / 되돌리지 못함 / 확인하지 못함 / 주차 상태가 아니어서 보류)와 원래 값을 보여 준다. 정리되지 않은 항목에는 [원래대로]와 [기록 지우기]를 둔다(그 항목의 이전 요청 응답을 기다리는 동안은 누를 수 없다, 6-1).

### 2-5. 다음 이용까지

| 사용자 행동 | 앱 반응 |
| --- | --- |
| 동승자가 늦어 다시 쉬려 한다 | **다시 쉬기**로 준비 화면에 간다. 지나지 않은 픽업 시각은 그대로 제안한다. 쉴 시간이 부족하면 스스로 미루지 않고, 사용자가 [지금 기준으로 다시 설정]으로 바꾼다(STEP 35) |
| 앱을 닫았다가 나중에 다시 연다 | 마지막 휴식 방식과 차량 연동 선택(목표 온도 포함)이 그대로다. 픽업 시각은 새로 제안한다 |
| 지난 휴식의 복원 기록이 남아 있다 | 준비 화면 위에 "지난 휴식에서 바뀐 설정이 남아 있을 수 있어요"와 항목별 현재 상태, [원래대로], [기록 지우기]를 보여 준다. [나중에]로 닫으면 기록은 남고 다음에 다시 보여 준다. 자동으로 쓰지 않는다. 응답을 받지 못한(완료 여부 불명) 기록은 [원래대로]·[기록 지우기]를 막고 조회와 수동 조정 안내만 한다(6-1) |
| 복원이 끝나기 전에 다시 쉰다 | 시작 조건이 맞으면 휴식은 시작한다. 정리되지 않은 항목은 이번 휴식에서 바꾸지 않는다(6-6) |
| 문을 닫거나 다시 P로 놓는다 | **자동으로 다시 시작하지 않는다** (근거: 4-4) |

## 3. 기능과 우선순위

"제품에 필요한 기능"과 "현재 구현 가능성"을 나눠 적는다. 실행 미확인이라는 이유로 요구사항을 후속으로 내리지 않는다. 지원이 안 되는 것으로 확인되면 근거와 대안을 붙여 Codex에 보고하고, 범위 조정은 Codex가 정한다.

| 준비 | 시작 조건 3개, 픽업 시각, 휴식 종료 시각, 쉴 수 있는 시간, 휴식 방식, 차량 연동 4개(등받이·무드등·바람·온도)와 지원 여부, 목표 온도, (있으면) 지난 복원 기록 | −5분/+5분, 휴식 소리 켬/조용히, 크기, 차량 연동 켬/끔, 목표 온도, 시작, [원래대로]·[기록 지우기]·[나중에] |
| 휴식 | 남은 시간, 종료 시각 (어두운 상태에서는 남은 시간만) | 화면 누르기 → 크기, 휴식 소리 켬/끔, 휴식 끝내기 |
| 종료 | 종료 이유, 종료 시각, 항목별 복원 상태와 원래 값 | 다시 쉬기, 정리되지 않은 항목의 [원래대로]·[기록 지우기] |

현재 구현(STEP 10)은 위 표와 이렇게 다르다: 준비 화면의 차량 연동은 무드등·바람·온도 3개이고, 등받이는 토글 없이 미지원 안내만 보여 준다(F11). 준비·휴식·종료·첫 안내의 주요 버튼([쉬기 시작]·[휴식 끝내기]·[다시 쉬기]·[확인했어요])은 내용 스크롤과 별개인 하단 고정 영역에 둔다. 어두운 휴식 화면에는 조작이 없다([verification/product-ui.md](verification/product-ui.md)).

Pleos 주의 분산 가이드에 따라 큰 터치 영역, 높은 대비, 짧은 문장을 쓴다. 정확한 최소 크기(dp)는 Pleos 디자인 가이드를 확인해 첫 구현 때 정한다. [미확인]

### 4-2. 휴식 상태

| 상태 | 들어가는 조건 | 화면 |
| --- | --- | --- |

| 시작 가능 | 시작 조건 모두 충족 | 준비 화면, 시작 버튼 활성 |
| 휴식 중 | 시작 누름 + (휴식 소리 켬이면) 포커스 획득 | 휴식 화면 |
| 종료 예고 | 휴식 중 + 종료 60초 전 | 휴식 화면, 소리 줄어듦 |
| 종료(정상) | 종료 시각 도달 | 종료 화면 |
| 종료(중단) | 2-4의 중단 원인 | 종료 화면, 중단 이유 |

차량 연동 항목(시트·조명·공조)별 상태는 6-1에 따로 정의한다. 항목 상태는 휴식 상태를 바꾸지 않는다. 차량 연동이 실패해도 휴식은 계속된다.

### 4-3. 예외 상황

| 상황 | 동작 | 이유 |
| --- | --- | --- |
| 기어·주행 제한 신호를 받을 수 없음 | 시작 불가. "차량 상태를 확인할 수 없어요" | 주차 확인은 안전 조건이다 |
| 주행 제한은 풀렸지만 P가 아님 (예: D + Auto Hold) | 시작 불가 | Pleos 주행 규제 문서(북미 외): "기어가 P단이 아니더라도 브레이크 시스템에 의해 차량이 제어되고 있다면 주행 규제가 해제됩니다." 쉬려면 P가 필요하다 |
| 조수석 문 신호 미지원 | 시작 불가. "이 차에서는 조수석 문 상태를 확인할 수 없어 시작할 수 없어요" | 문 상태 정책 [확정] |
| 조수석 문 상태 확인 중 | 시작 불가. "조수석 문 상태를 확인하고 있어요". 정해진 시간 안에 확인되지 않으면 오류로 바꿔 표시 | 문 상태 정책 [확정]. STEP 5 구현: 직접 조회 + 구독 + 1초 주기 조회, 응답 상한 2초를 넘기면 오류로 표시. 문을 여닫아야 시작되는 상황은 재현되지 않았다(실행 확인) |
| 조수석 문 신호 오류 (조회·구독 실패) | 시작 불가. "조수석 문 신호에 문제가 있어요" | 문 상태 정책 [확정] |
| 휴식 중 문 신호 끊김·오류 | 중단 종료. "차량 신호가 끊겨 휴식을 멈췄어요" | 동승자 도착 감지를 보장할 수 없다 |
| 시작 시 휴식 소리용 포커스 거부 | 시작하지 않고 "다른 소리가 재생 중이라 시작할 수 없어요". 조용히 모드는 시작 시 포커스가 필요 없다 | 포커스를 무시하고 재생하지 않는다 |
| 휴식 중 일시적 포커스 상실·감쇄 요청 | 5장 규칙 | |
| 휴식 중 영구 포커스 상실 (`AUDIOFOCUS_LOSS`) | 중단 종료 | 사용자가 다른 소리를 선택한 것으로 본다 |
| 시동 꺼짐 (Suspend 진입) | 중단 종료. 재생을 멈추고 포커스를 반납. 차량 연동 복원은 보장하지 않는다(6-1) | Pleos Suspend 가이드 |
| 다른 앱으로 이탈 | 중단 종료. 쓰기 조건이 맞으면 복원을 시도한다(완료 보장 없음, 6-1). 돌아오면 종료 화면을 보여 준다 | 사용자 선택. 앱 심사 가이드: "백그라운드로 이동했다가 돌아온 경우, 마지막 사용 중이던 상태가 복원되어야 합니다." |
| P 이탈 또는 주행 제한 | 즉시 중단 종료. 시트가 움직이는 중이면 `STOP`을 먼저 보내고, 모든 복원 쓰기를 보류한다(6-1) | 주행 안전. DO 미선언 앱은 Pleos 정책상 주행 중 사용 불가 |
| 차량 연동 적용·복원의 오류·타임아웃·부분 적용 | 6-1 "오류·타임아웃·부분 적용 처리", 6-6 상황별 처리 | 오류·타임아웃을 미변경의 증거로 삼지 않는다 |

### 4-4. 자동 재시작

**하지 않는다.** 종료 뒤 조건이 다시 맞아도(문 닫힘, P 복귀) 사용자가 다시 쉬기를 눌러야 시작한다.
- 문이 다시 닫혔다면 동승자가 이미 탔을 수 있다.
- P로 돌아왔다면 잠깐 이동 후 정차한 것일 수 있다. 쉴지는 사용자가 정한다.
- 꺼진 소리나 바뀐 차 설정이 갑자기 다시 바뀌면 놀라고 휴식을 방해한다.

## 5. 오디오와 종료 안내 규칙 [확정 정책 + 세부 제안]

### 5-1. 휴식 소리

- 휴식 소리 켬: 시작할 때 `AUDIOFOCUS_GAIN`을 요청한다. 거부되면 시작하지 않는다.
- 조용히: 휴식 소리만 끈다. 시작할 때 포커스를 요청하지 않는다. 종료 안내는 켬과 같은 규칙으로 낸다.
- 종료 예고: 종료 시각 60초 전부터 크기를 줄여 **종료 시각에 0이 되고 그때 멈춘다.** 종료 시각 이후에 휴식 소리를 더 재생하지 않는다.

### 5-2. 포커스 변화

| 이벤트 | 동작 |
| --- | --- |
| `AUDIOFOCUS_LOSS_TRANSIENT` | 휴식 소리를 일시정지한다. 휴식 세션은 계속된다. (Pleos 가이드: "`AUDIOFOCUS_LOSS_TRANSIENT` → 일시정지 후 복귀 가능") |
| `AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK` | 휴식 소리를 줄인다 |
| 포커스 복귀 (`AUDIOFOCUS_GAIN`) | 아래 세 조건을 **모두** 만족할 때만 재개한다. ① 같은 세션이 아직 진행 중 ② 현재 시각이 종료 시각 전 ③ 차량 조건(주차·주행 제한 없음·문 닫힘)이 유효. 종료 예고 구간이면 그 시각에 맞는 줄어든 크기로 재개한다. 하나라도 아니면 재개하지 않는다 |
| `AUDIOFOCUS_LOSS` | 중단 종료 |

**늦게 온 콜백 처리:** 휴식 세션마다 고유 번호를 둔다. 휴식 세션의 콜백(오디오 포커스, 플레이어, 차량 상태 변화)은 진행 중인 세션 번호와 같을 때만 처리한다. 이미 종료된 세션의 콜백으로는 휴식음을 재생하거나 세션 상태를 바꾸지 않는다. **차량 설정 쓰기(적용·복원) 작업의 응답은 이 규칙의 대상이 아니다.** 세션과 별개로 작업 식별자로 끝까지 처리한다(6-1).

### 5-3. 종료 안내 (정상 종료에서만)

| 단계 | 동작 |
| --- | --- |
| 준비 | 휴식 시작 때 TextToSpeech를 `Mode.ON_DEVICE`로 초기화한다. 실패하면 이번 세션은 음성 없이 안내음만 쓴다. 안내음 파일은 앱에 포함한다 |
| 종료 시각 | 휴식 소리가 멈춘 뒤 안내용 포커스를 확보한다. 휴식 소리 켬이면 가지고 있던 포커스를 안내 후 반납하고, 조용히면 이때 일시 포커스(`AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`, [제안])를 요청한다 |
| 포커스 확보 | 안내음 1회 → 음성 "픽업 2분 전이에요" 1회 → 포커스 반납 |
| 포커스 거부 | 소리 없이 화면 안내만 한다. Pleos 포커스 매트릭스에는 거부(R) 조합(예: 통화 중)이 있다 |
| 음성 실패 (초기화 실패, `onError`, 권한 거부) | 안내음만 낸다 |
| 안내음 재생 실패 | 화면 안내만 한다 |

- 포커스를 무시하고 재생하지 않는다. **반드시 깨워 준다고 보장하지 않는다.** 첫 실행 안내에 이 한계를 적는다(2-1).
- 갑작스러운 중단·직접 종료에서는 안내음·음성을 내지 않는다.
- TextToSpeech SDK가 오디오 포커스를 스스로 요청하는지는 문서에 없다. STEP 6 실행 확인: Speech Service는 포커스를 요청하지 않았고, 발화 중 CarAudioFocus의 보유자는 앱(USAGE_MEDIA)뿐이었다. 그래서 앱이 포커스를 잡은 동안에만 말하고, 포커스를 잃으면(LOSS·LOSS_TRANSIENT) `stop()`한다.

## 6. 차량 제어 쓰기 계약 [확정 기능 + 세부 제안]

### 6-1. 공통 규칙

**휴식 세션과 차량 제어 작업**
- 휴식 세션: 시작부터 종료까지. 소리·화면·종료 판단을 맡는다.
- 차량 제어 작업(이하 작업): 한 항목·영역에 대한 적용 또는 복원 쓰기 1건. 작업마다 고유 식별자가 있고 복원 기록과 연결된다. **휴식 세션이 끝나도 작업은 끝까지 처리한다.**

**적용 조건:** 휴식 시작 시점에 사용자가 그 항목을 켰고, capability 확인을 통과했고, 그 항목·영역에 정리되지 않은 이전 기록이 없을 때만 적용 작업을 만든다. 실제 쓰기는 아래 "쓰기 직전 확인"을 다시 통과해야 한다.

**작업 상태**

| 상태 | 뜻 | 복원 기록 |
| --- | --- | --- |
| 요청 안 함 | 변경 명령을 보내지 않은 것이 **확실함**. 이 실행 안에서 보내기 전에 멈춤(사용자가 끔, 미지원, 쓰기 직전 확인 불통과, 기록 저장 실패, 이전 기록 미정리) | 없음 |
| 변경 요청 중 | 기록 저장 후 변경 명령을 보냈거나 보내려던 중. 종료 콜백(`onComplete`/`onFailed`)을 아직 받지 못함 = **미완료 요청**. 타임아웃이 지나도 이 단계를 유지하고, 화면에는 "결과 불명(응답 대기)"으로 표시 | 있음 |
| 적용 확인 | 적용 요청의 정상 응답(`onComplete`)을 받은 뒤 재조회 값이 목표값과 같음 | 있음 |
| 결과 불명·부분 적용 | 종료 콜백 뒤 재조회 값이 목표값과 다르거나 재조회 실패. 또는 이전 실행에서 보내고 응답 기록이 없는 요청(완료 여부 불명) | 있음 |
| 복원 중 | 원래값 쓰기 명령을 보냈거나 보내려던 중. 종료 콜백 미수신 = 미완료 요청. 타임아웃이 지나도 유지 | 있음 |
| 복원 확인 | 그 항목·영역에 미완료 요청과 완료 여부 불명 요청이 없고, 원복 요청의 정상 응답(`onComplete`)을 받은 뒤 재조회 값이 원래값과 같음(시트는 허용 오차 이내). `onFailed`는 값과 관계없이 복원 확인이 아니다 | 삭제 |
| 복원 실패 | 원복 요청이 `onFailed`로 끝났거나, 정상 응답 뒤 재조회 값이 원래값과 다르거나 재조회 실패·응답 없음 | 있음 |
| 복원 보류 | 쓰기 조건이 맞지 않아 복원 명령을 보내지 않음 | 있음 |
| 사용자 변경 | 사용자가 직접 바꾼 것으로 판정 | 있음(자동 복원 안 함) |

**복원 기록** [PM 결정: 채택]
- **차량 변경 명령을 보내기 전에** 앱 내부 저장소에 저장한다: 기록 형식 버전, 작업 식별자, 대상 항목과 영역, 변경 전 값, 요청할 목표값, 처리 단계(위 상태).
- 저장이 실패하면 그 항목에는 변경 명령을 보내지 않는다(요청 안 함). 휴식과 다른 항목은 계속한다.
- 상태가 바뀔 때마다 처리 단계를 갱신한다. 복원 명령 전에도 단계를 "복원 중"으로 갱신하고, 갱신이 실패하면 복원 명령을 보내지 않는다.
- 삭제는 두 경우뿐이다. ① 복원 확인(위 표의 정의). **재조회 값이 원래값이라는 것만으로는 삭제하지 않는다.** ② 사용자가 [기록 지우기]를 명시적으로 고름. 그 항목에 미완료 요청이 있는 동안은 받지 않는다.
- 오류·타임아웃만으로는 삭제하지 않는다. 안내를 [나중에]로 닫는 것은 삭제가 아니다.

**미완료 요청과 타임아웃**
- 미완료 요청: 이 실행에서 보냈고 종료 콜백(`onComplete`/`onFailed`)을 아직 받지 못한 쓰기 요청.
- **타임아웃은 요청을 끝내지 않는다.** 응답 대기 상한이 지나면 화면에 결과 불명(응답 대기)을 표시하고 현재값을 재조회해 보여 줄 뿐이다. 재조회 값이 원래값이어도 요청이 나중에 반영될 수 있으므로 기록을 유지한다. 재조회로 요청의 순서나 완료를 판단하지 않는다.
- 미완료 요청이 있는 항목·영역에는 새 적용·복원 쓰기를 보내지 않는다. 사용자의 [원래대로]·[기록 지우기]도 받지 않고, 응답 대기 문구와 원래값, 수동 조정 방법을 보여 준다. 예외는 시트 `STOP`뿐이다.
- 종료 콜백이 늦게 오면 작업 식별자로 기록을 찾아 미완료 요청을 끝내고, 현재값을 다시 조회해 위 표대로 상태를 정한다. 휴식이 끝난 뒤라면 그 결과로 복원이 필요한지 판단한다.
- 이전 실행에서 응답 수신 표시 없이 남은 기록은 단계 이름("변경 요청 중"·"복원 중"·"적용 확인"·"결과 불명" 등)과 관계없이 이 실행에서 응답을 받을 수 없어 완료 여부를 알 수 없다. 결과 불명으로 보고, 원래값이 조회돼도 자동으로 지우지 않는다. 기록이 "변경 요청 중"이면 명령 직전에 앱이 끝났더라도 보냈을 수 있는 것으로 본다. 보내지 않은 것이 확실한 경우는 "요청 안 함"뿐이다.
- SDK 근거: 공개 문서는 "Vehicle SDK가 제공하는 비동기 API는 onComplete와 onFailed 콜백으로 결과를 전달합니다"라고만 적는다([오류 코드][p-error]). 응답 시간 상한, 요청 취소, 여러 요청의 처리 순서, 종료 콜백 뒤 값이 다시 바뀌지 않는다는 보장은 확인하지 못했다. 그래서 결과 불명 항목을 자동으로 복구할 수 있다고 단정하지 않고, 사용자 안내와 수동 조정 방법으로 처리한다. [검증 항목]
- 조회(지원 확인·스위치·밝기·재조회)에는 쓰기와 별도의 응답 대기 상한을 둔다. 조회가 시간을 넘기면 그 조회만 실패로 끝내고 쓰지 않으며, 그 뒤에 온 늦은 조회 응답은 무시한다. 쓰기 타임아웃과 달리 기록·잠금을 만들지 않는다.
- 기록 저장·갱신·삭제가 한 번이라도 실패하면 저장 오류 상태가 된다. 이후 차량 쓰기와 기록 삭제를 하지 않고, 성공·원복 완료로 표시하지 않는다.
- 화면을 닫으면(close) 또는 더 새로운 관리자가 기록을 맡으면, 이전 관리자는 늦게 온 콜백을 상태·기록에 반영하지 않는다. 미완료 쓰기 기록은 디스크에 그대로 남는다. 기록을 맡는 관리자는 한 번에 하나다.

**쓰기 직전 확인 (적용·복원 공통)**

적용뿐 아니라 복원도 차량 설정을 쓰는 작업이다. 각 쓰기 명령 직전에 다시 확인하고, 하나라도 아니면 쓰지 않고 보류한 뒤 기록과 상태를 표시한다.
1. 최신 차량 조건: P 기어 + 주행 제한 없음이 확인됨
2. 작업 유효: 적용이면 휴식 세션이 아직 진행 중. 복원이면 기록이 남아 있고, 자동 복원이면 사용자 변경으로 판정되지 않음
3. 같은 항목·영역에 미완료 요청이 없음
4. 복원 기록 저장·갱신 성공
5. 복원이면 현재 capability를 다시 조회해 기록 영역의 지원, 읽기·쓰기, 원래값이 허용 범위 안인지 확인한다. 조회 실패·응답 없음이면 쓰지 않는다

1~3을 확인한 뒤 4(기록 저장·갱신)를 하고 곧바로 명령을 보낸다.

예외: 시트 `STOP`은 움직임을 멈추는 명령이라 조건과 관계없이 바로 보낸다.

**오류·타임아웃·부분 적용 처리**
1. 오류나 타임아웃을 "바뀌지 않았다"는 증거로 삼지 않는다.
2. 시트는 일부 움직였을 수 있으므로 먼저 `STOP`을 시도한다.
3. 타임아웃(종료 콜백 없음): 요청은 미완료로 남는다. 현재값을 재조회해 보여 주되, 값이 목표값이든 원래값이든 상태는 결과 불명(응답 대기)이고 기록 단계는 그대로 둔다. 그 항목·영역에는 새 쓰기를 보내지 않는다.
4. 종료 콜백(`onComplete` 또는 `onFailed`)을 받은 뒤: 현재값을 다시 조회한다.
   - `onComplete` + 재조회 목표값 → 적용 확인
   - `onFailed` → 재조회 값과 관계없이 결과 불명, 기록 유지. `onFailed` 수신을 실제 값이 바뀌지 않았다는 보장으로 보지 않는다
   - `onComplete`인데 재조회가 목표값과 다름 → 부분 적용·결과 불명. 이번 세션에서는 그 항목을 더 바꾸지 않고, 종료 때 복원 대상으로 둔다
   - 조회 실패·응답 없음 → 결과 불명, 기록 유지
5. 결과 불명 항목에는 미확인 상태, 원래값, 수동 조정 방법을 알린다.
6. 실패나 결과 불명을 성공·원복 완료로 표시하지 않는다.

**세션 종료 뒤 처리**
- 휴식이 끝나면 소리 재생과 새 적용 작업을 멈춘다. 이동 중인 시트에는 `STOP`을 보낸다.
- 종료 뒤 도착한 적용 응답도 버리지 않는다. 작업 식별자로 기록을 찾아 재조회 결과를 반영하고 복원 대상에 넣는다.
- 복원 작업의 응답은 종료 뒤에도 처리한다.
- 늦은 응답은 그 작업의 기록과 항목 상태만 바꾼다. 휴식음을 재생하거나 새 세션 상태를 바꾸지 않는다.
- 같은 항목·영역에 적용과 복원을 동시에 요청하지 않는다. 적용 요청의 종료 콜백을 받은 다음에만 복원한다. 타임아웃 뒤 재조회는 확정으로 보지 않는다.
- 이전 작업이 정리되지 않은 항목(기록이 남은 항목)은 새 세션이 덮어쓰지 않는다.

**사용자 변경 판정**

적용 확인 뒤 앱의 쓰기가 진행 중이 아닐 때 리스너 값이 앱이 설정한 목표값과 달라지면 사용자가 직접 바꾼 것으로 본다. 그 항목은 이후 적용하지 않고 **기존 기록으로 자동 복원하지 않는다.** 기록은 남기고, 종료 화면·다음 실행 안내에 "직접 바꾸셔서 그대로 뒀어요"와 [원래대로]·[기록 지우기]를 보여 준다. 사용자가 [원래대로]를 직접 고를 때만 복원한다.

**종료 종류별 복원**

| 종료 | 시트 | 조명·공조 |
| --- | --- | --- |
| 정상 종료, 직접 종료, 문 열림, 오디오 영구 상실, 문 신호 끊김 | 이동 중이면 `STOP` → 쓰기 직전 확인 통과 시 복원 | 쓰기 직전 확인 통과 시 복원 |
| P 이탈·주행 제한 | 이동 중이면 `STOP` 우선 시도 → 복원 보류 [PM 결정] | 쓰기 조건 불충족 → 복원 보류 |
| 다른 앱으로 이탈 | `STOP` → 확인 통과 시 복원 시도 | 확인 통과 시 복원 시도 |
| 시동 꺼짐, 앱 강제 종료 | 복원을 보장하지 않는다. 기록이 남는다 | 같음 |

- 앱 이탈 때 시작한 복원을 화면 밖에서 끝까지 마칠 수 있는지는 미확인이다. 완료를 보장하지 않는다.
- **보류·결과 불명·복원 실패·사용자 변경 기록은 자동으로 다시 쓰지 않는다** [PM 결정]. 종료 화면이나 다음 실행 안내에서 사용자가 [원래대로]를 누르면, 그 항목에 미완료 요청이 없을 때만 쓰기 직전 확인을 거쳐 원래값으로 복원한다. 결과는 종료 콜백과 재조회로 확인한다.
- 다음 실행 때는 기록을 불러와 보여 주고, 쓰기 없이 조회만 한다. 조회 결과만으로 기록을 지우지 않는다.
- 응답 수신 표시가 없는 기록(단계 이름과 관계없이)이나 이전 요청 결과 불명 표시가 있는 기록은, 재실행 뒤에도 앱의 새 설정·[원래대로]·[기록 지우기]를 모두 막는다 [PM 결정]. 조회와 수동 조정 안내만 한다. 재실행이나 앱 데이터 삭제로 이 잠금을 우회하지 않는다.

**표시 문구**
- 요청 안 함: "설정을 기록하지 못해 ○○은 바꾸지 않았어요" / "○○은 이 차에서 지원하지 않아요" / "이전 휴식의 ○○을 정리하는 중이라 이번에는 바꾸지 않아요"
- 응답 대기(미완료 요청): "○○ 변경 결과를 기다리고 있어요. 급하면 차량에서 직접 조정해 주세요 (원래 값: …)"
- 결과 불명·부분 적용: "○○이 바뀌었는지 확인하지 못했어요. 차량에서 직접 확인해 주세요 (원래 값: …)"
- 복원 실패: "○○을 원래대로 돌리지 못했어요. 직접 조정해 주세요 (원래 값: …)"
- 복원 보류: "주차 상태가 아니어서 ○○을 돌리지 않았어요. 정차 후 [원래대로]를 누르거나 직접 조정해 주세요"
- 응답 대기 시간 상한은 실행 검증 후 정한다.

### 6-2. 시트 — 편한 자세

| 항목 | 계약 |
| --- | --- |
| 사용자에게 제공할 동작 | 휴식 시작 때 운전석 등받이를 뒤로 젖히고, 종료 때 원래 위치로 되돌린다 |
| 대상 | 운전석 `SeatArea(SeatValue.ROW_1_LEFT)`의 등받이 각도. 조수석은 픽업 상대가 앉을 자리라 건드리지 않는다 |
| 조회 API·권한 | `checkSeatBackrestAnglePositionCapabilities(onComplete: (CapabilityConfig, Map<SeatArea, AreaBounds<Int>>))`, `getCurrentSeatBackrestAnglePosition(area, onComplete: (Int?))`, `registerSeatBackrestAnglePosition(area, SeatBackrestAnglePositionListener)` → `onSeatBackrestAnglePositionUpdated(position: Int?)`. 권한 `pleos.car.permission.CAR_SEATS` |
| 제어 API·권한 | `checkMoveSeatBackrestAngleCapabilities(onComplete: (CapabilityConfig, List<SeatArea>))`(`CAR_SEATS`), `moveSeatBackrestAngle(area, value: MoveControl, onComplete: (SeatArea, MoveControl?), onFailed)`(`pleos.car.permission.CONTROL_CAR_SEATS`) |
| 방향 제어와 목표 위치 | Pleos는 **방향 제어만** 제공한다(`MoveControl` = `BACKWARD` / `STOP` / `FORWARD`). 숫자 위치를 지정하는 API는 없다. 파라미터 설명("The target seat backrest angle to set")은 타입과 어긋나므로 타입 기준으로 보고 검증한다. 따라서 위치를 구독하면서 목표에 닿으면 `STOP`을 보내는 방식으로 움직인다. **고정 시간만 움직여 원하는 각도나 원위치에 도달한다고 가정하지 않는다** |
| 지원·범위 확인 | 운전석이 ① 이동 capability 목록에 있고 accessType에 쓰기가 있으며 ② 위치 capability에 있고 읽기가 있고 min/max가 있어야 한다. 하나라도 없으면 시트는 쓰지 않는다. 위치를 읽지 못하면 원위치 확인이 불가능하므로 움직이지 않는다 |
| 목표 위치 | 시작 위치에서 뒤로 일정량. min/max를 넘지 않는다. **이동량은 실행 검증 후 정한다** [PM 결정]. 위치 값의 단위와 `BACKWARD`가 값을 키우는지 줄이는지는 문서에 없어 검증 항목이다 |
| 변경 전 값 | 이동 명령 전에 `getCurrentSeatBackrestAnglePosition`으로 읽고, 목표 위치와 함께 복원 기록에 저장한다. 저장 실패면 움직이지 않는다 |
| 변경 성공 확인 | 이동 중 위치 값이 목표 방향으로 변하는지 감시한다. 목표에 닿으면 `STOP`을 보내고, 이동·`STOP` 요청의 종료 콜백을 받은 뒤 다시 조회해 허용 오차 안이면 적용 확인. `onFailed`, 정해진 시간 안에 값 변화 없음, 반대 방향 변화, 최대 이동 시간 초과, 범위 끝 도달 중 하나면 즉시 `STOP`을 시도하고 6-1 오류 처리(재조회 → 원래값·목표값 비교)를 따른다. **일부 움직였을 수 있으므로 미변경으로 보지 않는다** |
| 취소·중단·주행 전환 | 어떤 종료든 이동 중이면 먼저 `STOP`. 이동 중 주행 전환이 감지되면 `STOP`을 우선 시도하고 복원 이동은 보류한다 [PM 결정]. 주행 중 시트가 움직이면 위험하고, Pleos 주행 규제 정책은 주행 중 "도어, 시트, 차량 설정"을 제한한다. `STOP` 응답이 없으면 위치 리스너로 멈췄는지 확인하고, 확인되지 않으면 결과 불명으로 표시한다 |
| 복원 조건과 확인 | 6-1 쓰기 직전 확인을 통과하고 사용자 변경이 없을 때, 기록한 원래 위치 방향으로 이동한다. 허용 오차 안에 들어오면 `STOP` → 재조회로 복원 확인. 복원 이동 중 오류는 `STOP` → 재조회 → 6-1 표대로 판정(종료 콜백을 받지 못한 요청이 있으면 결과 불명) |
| 사용자 직접 변경 | 앱이 이동 명령을 보내지 않는 동안 위치가 바뀌거나 명령과 반대로 바뀌면 사용자 조작으로 본다. 즉시 `STOP`하고, 이후 시트는 움직이지 않으며 복원하지 않는다 |
| 실패 표시 | 6-1 표시 문구(○○ = 운전석 등받이). 위치 값은 단위가 문서에 없으므로 숫자 대신 "시트 스위치로 원래 자세에 맞춰 주세요"로 안내한다 |
| 검증 항목 | Virtual Console에 등받이 카드가 없음 → 에뮬레이터에서 이동 명령에 위치 값이 바뀌는지, 위치 갱신 주기, `STOP` 지연으로 인한 초과 이동, 방향 부호, 단위 |

STEP 7 bench의 색 적용 결과(결과 불명)는 소급해 바꾸지 않는다 |
| 취소·중단·주행 전환 | 6-1 표대로. 쓰기 직전 확인(P + 주행 제한 없음)을 통과할 때만 복원하고, 주행 전환이면 복원 보류 |
| 복원 조건과 확인 | 쓰기 직전 확인을 통과하고 사용자 변경이 없는 영역·속성만 원래값으로 설정 → 재조회로 복원 확인 |
| 사용자 직접 변경 | 리스너 값이 앱 설정값과 다르면 그 영역·속성은 복원하지 않는다. [STEP 8 실측·보완] 리스너 알림만으로는 정하지 않는다(구독 직후 오래된 캐시값이 올 수 있음). 불일치 알림 → 별도 현재값 재조회 → 실제 값이 앱 값과 다를 때만 사용자 변경으로 본다. 조회가 끝났을 때 같은 작업·요청이고 적용 확인 상태이며 진행 중 요청·복원이 없을 때만 반영한다. 종료 직전 조회도 같은 기준이다 |
| 실패 표시 | 6-1 표시 문구(○○ = 무드등). 원래 밝기·색을 함께 보여 준다 |

### 6-6. 상황별 처리

| 상황 | 복원 기록 | 동작·표시 |
| --- | --- | --- |
| 명령 전에 기록 저장 실패 | 만들지 못함 | 그 항목은 변경 명령을 보내지 않는다(요청 안 함). 휴식과 다른 항목은 계속. "설정을 기록하지 못해 ○○은 바꾸지 않았어요" |
| 실제 변경 후 응답 타임아웃 | "변경 요청 중" 그대로 유지(미완료 요청) | 미변경으로 보지 않는다. 재조회 값을 보여 주되 상태는 결과 불명(응답 대기). 재조회가 원래값이어도 기록을 지우지 않는다. 종료 콜백이 올 때까지 그 항목에는 새 적용·복원 쓰기, 사용자 [원래대로]·[기록 지우기]를 받지 않는다 |
| 타임아웃 뒤 원래값 조회, 그 뒤 늦게 반영·응답 도착 (예: 밝기 80 → 30 요청) | 계속 "변경 요청 중" → 응답 도착 후 재조회 결과로 갱신 | 응답 도착 → 작업 식별자로 기록을 찾아 미완료 요청을 끝냄 → 재조회 30 = 목표값 → 적용 확인. 휴식 중이면 휴식을 계속하고, 끝났으면 쓰기 직전 확인을 거쳐 80으로 복원. 그사이 다른 쓰기는 겹치지 않는다 |
| 시트 일부 이동 후 오류 | 결과 불명·부분 적용, 유지 | `STOP` 시도 → 재조회 → 원래값·목표값과 다르면 부분 적용. 이번 세션에서는 더 움직이지 않는다. 이동·`STOP` 요청의 종료 콜백을 모두 받은 뒤, 종료 때 쓰기 직전 확인을 통과하면 원래 위치로 복원. 콜백을 못 받았거나 조회도 실패하면 결과 불명과 수동 조정 방법 표시 |
| 휴식 종료 후 늦은 적용 응답 | 작업 식별자로 찾아 미완료 요청을 끝내고 갱신, 유지 | 종료 콜백을 받은 뒤 재조회로 결과를 정한다. 복원이 필요하면 그때 쓰기 직전 확인을 거쳐 복원한다(응답 전에는 복원하지 않음). 휴식음 재생·새 세션 상태 변경 없음 |
| 복원 중 다시 쉬기 | "복원 중" 유지 | 시작 조건이 맞으면 새 휴식은 시작한다. 그 항목은 이번 휴식에서 적용하지 않는다("이전 휴식의 ○○을 정리하는 중이라 이번에는 바꾸지 않아요"). 복원 응답은 계속 처리하고 확인되면 기록을 지운다. 이번 세션 도중에는 다시 적용하지 않는다 |
| 사용자 직접 변경 | "사용자 변경"으로 유지 | 이후 적용·자동 복원 없음. 종료 화면에 "직접 바꾸셔서 그대로 뒀어요"와 [원래대로]·[기록 지우기] |
| 주차 조건 상실 | 유지, 대상 항목은 "복원 보류" | 휴식 중단 종료. 시트 이동 중이면 `STOP` 우선. 적용·복원 쓰기를 모두 보류한다. 조건이 돌아와도 자동으로 쓰지 않고, 사용자가 [원래대로]를 누르면 쓰기 직전 확인을 거쳐 복원 |
| 복원 중 앱 강제 종료 후 재실행 | "복원 중"으로 남음(완료 여부 불명) | 다음 실행 때 쓰기 없이 현재값을 조회해 보여 준다. 응답을 받지 못한 요청이라 원래값이어도 지우지 않고 결과 불명으로 안내한다. 앱의 새 설정·[원래대로]·[기록 지우기]는 막고 조회와 수동 조정 방법만 안내한다. 자동으로 쓰지 않는다 |

### 7-4. 남은 기술적 미확인 사항 (검증 순서대로)

1. 차량 제어 API: 앰비언트 밝기 설정과 요구 권한(`CAR_LIGHTS` + `CONTROL_CAR_LIGHTS`)은 STEP 3 보완에서 실행 확인. 풍량·온도 설정·원복은 STEP 7에서 실행 확인. 색: set 문서는 alpha를 `0xFF` 고정으로 적지만, 차량은 RGB만 저장하고 조회·리스너는 항상 alpha `0x00`을 돌려줬다(요청 `0xFFFF9A40` → `0x00FF9A40`, 원복 `0x00FFFFFF` → `0x00FFFFFF`). STEP 8 PM 결정: RGB로 비교하고 alpha는 00/FF만 허용, 요청은 항상 alpha FF. 이 기준으로 제품 적용·복원 실행 확인
2. 앰비언트 스위치: 정상 차량 설정 UI(라이트 > 무드 조명 [켜기]/[끄기])로 바꾸면 SDK `getAmbientLightSwitch`도 ON/OFF로 따라온다(실행 확인). Virtual Console의 숨김 항목 `ambient_light.mode`는 차량 스위치와 무관하게 On으로 남는다. Virtual Console을 처음 열면 콘솔 값(앰비언트 밝기 100% 등)이 차량에 발행됐다(관찰). 기어 P 읽기는 실행 확인됨
3. 시트: 위치 조회(0~100)와 이동 지원은 STEP 4에서 실행 확인. STEP 7: 이동·STOP 명령은 `onComplete`를 받고 내부 actuator도 움직였지만(내부 raw 값은 FORWARD에서 커지고 BACKWARD에서 작아짐, 약 0.1초마다 0.05, Console recline 0→45→0), 공개 위치 조회·구독은 계속 0이었다. 공개 SDK 기준 이동량·방향 부호·단위·허용 오차·원복 판정은 미확인(이 에뮬레이터의 불일치인지 실제 차량도 같은지 미확인). 다른 공개 정밀 조회 경로는 없다(`checkSeatBackrestAngleCapabilities`는 deprecated)
4. 풍량·온도 변경이 공조 자동 모드·전원에 주는 영향, 듀얼 영역 동기화. 온도 선택 간격(`incrementCelsius`)은 0.5°C로 조회됨(STEP 4). STEP 7: 이 에뮬레이터에서는 풍량 변경(Auto false·true)과 온도 변경(Auto false)이 Auto·전원·Dual을 바꾸지 않았다. 공조 패널 Sync가 SDK Dual true에 대응하고, 그때 운전석 온도 변경이 조수석에도 같은 값으로 반영됐다. STEP 9: Auto true에서도 풍량·온도 적용이 Auto를 바꾸지 않았다(실기). 제품은 명령 전후 Auto·전원·Sync가 바뀌거나 읽히지 않으면 출처를 추측하지 않고 그 그룹을 결과 불명으로 멈춘다. `setHvacAuto`는 [원래대로]에서만 쓰며 실기 확인(Auto true 원래 → 휴식 중 차량 UI로 Auto 끔 → 종료 때 보존 → [원래대로]에서 Auto true 복원). Auto가 실제로 풍량을 다시 바꾸는 차량의 동작은 미확인
5. 쓰기 응답 시간(타임아웃 기준), 타임아웃 뒤 늦은 응답·반영이 실제로 오는지. 요청 취소, 처리 순서, 종료 콜백 뒤 값 불변은 문서에 없음. STEP 7 실기의 `onComplete`는 0.07~0.33초 안에 왔고 늦은 응답·`onFailed`는 재현되지 않았다(단위 테스트로만 확인)
6. TextToSpeech: `ON_DEVICE` 한국어 합성·재생과 포커스 주체(앱)는 STEP 6에서 실행 확인(이벤트·트랙·포커스 기록 기준). 스피커로 실제 들리는지는 미확인: 에뮬레이터 오디오 출력을 켜면 호스트 CoreAudio 초기화에서 멈춰 출력이 꺼진 상태로만 시험했다([verification/rest-audio.md](verification/rest-audio.md))
7. 화면을 벗어난 뒤 복원을 끝까지 마칠 수 있는지. STEP 8 무드등: 프로세스 단위 owner(전용 Handler·Vehicle·주차 소스)로, 다른 앱이 화면을 가린 상태(Activity onStop)에서 복원 완료를 **실행 확인**했다. 프로세스가 강제로 끝나면 보장하지 않는다(기록이 남아 다음 실행에 안내)
8. `CarUxRestrictionsManager` 사용 권한
9. 문 상태 초기 "확인 중" 지연: STEP 4에서 직접 조회는 앱 시작 약 5초 뒤에도 열린 문을 바로 `1`로 줬다. 새 프로세스의 첫 문 구독 알림은 등록 1.6~1.8초 뒤에 왔고, STEP 4 보완에서는 첫 알림이 아예 오지 않은 경우도 있었다. 따라서 시작 조건은 직접 조회값으로 정하고, 구독은 변화 감지에만 쓴다. 직접 조회를 쓰면 문을 여닫아야 풀리는 멈춤은 재현되지 않았다. 앱 표시 직후 3초 안의 조회는 측정하지 못했다. STEP 5: 화면이 보이는 동안만 직접 조회 + 구독 + 1초 주기 조회(응답 상한 2초)로 구현했다. 문·기어 변화는 구독·콜백으로 0.2초 안에 반영됐다. 새 프로세스 시작 직후 첫 capability 응답이 2초를 넘겨 오류 문구가 약 1초 보인 뒤 재시도로 확인된 경우가 있었다(문을 연 채 시작해도 닫힘으로 보이거나 시작이 허용되지 않음, [verification/rest-flow.md](verification/rest-flow.md))

## 8. 데이터와 콘텐츠 [제안]

### 8-1. 읽는 차량 데이터

| 데이터 | 사용 목적 |
| --- | --- |
| 기어, 주행 제한 | 시작 조건, 주행 전환 종료, 시트 복원 가능 여부 |
| 조수석 문 위치 | 시작 조건, 문 열림 종료 |
| 운전석 등받이 위치 | 변경 전 값 저장, 이동 감시, 복원 확인, 사용자 변경 감지 |
| 앰비언트 밝기·색·스위치 | 변경 전 값 저장, 변경·복원 확인, 사용자 변경 감지 |
| 풍량, 목표 온도, 공조 전원·자동 상태 | 같음 |

외부로 보내지 않는다. 검증용 앱 로그에는 상태 이름, 값, 시각만 남긴다. 개인정보는 없다.

### 8-2. 쓰는 차량 설정 (쓰기 대상)

| 대상 | 언제 | 범위 |
| --- | --- | --- |
| 운전석 등받이 각도 (`moveSeatBackrestAngle`) | 휴식 시작(젖힘), 종료(복원) | 지원 범위 안, 주차 중에만 이동 |
| 앰비언트 밝기·색 (`setAmbientLightBrightness`, `setAmbientLightBrightnessColor`) | 시작(낮춤), 종료(복원) | capability 영역, 스위치 ON일 때만 |
| 풍량 (`setHvacFanSpeed`) | 시작(낮춤), 종료(복원) | capability 영역, 전원 ON일 때만 |
| 목표 온도 (`setHvacTemperature`) | 시작(사용자가 고른 값), 종료(복원) | 운전석 포함 영역, capability 범위 안, 전원 ON일 때만 |
| 공조 자동 상태 (`setHvacAuto`) | [원래대로] 때만(STEP 9 PM 결정: 출처를 알 수 없는 Auto 변화는 자동으로 되돌리지 않음) | 그룹의 첫 변경 전에 한 번 저장한 원래 값으로만, 최대 1회 |

적용은 사용자가 시작한 휴식 세션 안에서 사용자가 켠 항목만 쓴다. 복원은 기록이 있는 항목만 쓴다. 모든 쓰기는 명령 전 기록 저장과 쓰기 직전 확인(6-1)을 통과해야 한다(시트 `STOP`만 예외).

현재 구현(STEP 9 기준): 제품 휴식이 실제로 쓰는 것은 앰비언트 밝기·색(STEP 8), 풍량·운전석 목표 온도(STEP 9), [원래대로] 때의 공조 자동 상태(STEP 9)다. 등받이는 제품 자동 제어를 막아 두어 쓰지 않는다(F11). 공조 전원·연동(Sync)은 앱이 켜거나 끄지 않는다. 위 표는 처음 설계한 쓰기 대상 전체다.

### 8-3. 저장하는 데이터

| 항목 | 저장 위치 | 보관·삭제 |
| --- | --- | --- |
| 휴식 소리 켬/조용히, 소리 크기 | 앱 전용 내부 저장소 | 앱 삭제나 앱 데이터 삭제 때 삭제 |
| 차량 연동 켬/끔과 고른 목표 온도. 요구: 시트·무드등·바람·온도 4개 / 현재 저장 구현: 무드등·바람·온도(시트는 제품 제어가 막혀 있어 저장 키가 아직 없음) | 같음 | 같음 |
| 첫 실행 안내를 봤는지 | 같음 | 같음 |
| 복원 기록 (기록 형식 버전, 작업 식별자, 항목·영역, 변경 전 값, 요청할 목표값, 처리 단계) | 같음. 차량 변경 명령 **전에** 저장 | 복원 확인(6-1 정의: 응답을 받지 못한 요청이 없고, 원복 정상 응답 + 재조회 원래값) 또는 사용자의 [기록 지우기] 때만 삭제(완료 여부 불명 기록은 [기록 지우기]도 막음). 오류·타임아웃, 타임아웃 뒤 원래값 조회, [나중에]로는 지우지 않는다 |

- 픽업 시각은 저장하지 않는다. 같은 실행 안에서 "다시 쉬기" 제안에만 쓴다.
- 복원 기록에는 차량 설정 값만 들어가고 개인정보는 없다.
- 매니페스트의 `android:allowBackup="false"`를 유지해 기기 백업에 넣지 않는다. Android 12 이상에서는 이 값만으로 기기 간 이전이 막히지 않을 수 있어(Android 공개 문서), `dataExtractionRules`(cloud-backup·device-transfer 모두 앱 영역 제외)와 Android 11 이하용 `fullBackupContent`를 함께 둔다(STEP 5).
- STEP 6 구현: SharedPreferences `comma_cabin_rest`에 첫 실행 안내 버전(`onboarding_version`), 휴식 소리 켬/조용히(`rest_sound`), 크기(`rest_level`)만 저장한다(STEP 5의 `onboarding_seen`은 새 안내를 본 것으로 인정하지 않고 판단에도 쓰지 않으며, 새 안내 버전을 저장할 때 지운다. 잘못된 값은 조용히·보통·안내 미확인으로 처리). 픽업 시각·이용 기록은 저장하지 않는다. 기존 복원 기록 파일은 건드리지 않는다.
- STEP 8 구현: 같은 SharedPreferences에 [무드등 조정] 켬/끔(`rest_lighting`, 없거나 형식이 틀리면 켬)을 더했다. 휴식 무드등 복원 기록은 새 파일 `rest-lighting-records.json`(형식 버전 1, 임시 파일 → fsync → 원자적 이동 → 디렉터리 fsync)에 둔다. STEP 3 밝기 기록·STEP 7 bench 기록 파일은 읽기만 하고 바꾸지 않는다. 형식은 [verification/rest-lighting.md](verification/rest-lighting.md)
- STEP 9 구현: 같은 SharedPreferences에 `rest_fan`·`rest_temp`(없거나 형식이 틀리면 켬)와 `rest_temp_c`(없거나 유한하지 않으면 22.0)를 더했다. 공조 복원 기록은 새 파일 `rest-climate-records.json`(형식 버전 1, 그룹 단위, 같은 원자적 저장)에 둔다. 다른 기록 파일은 바꾸지 않는다. 형식은 ([verification/rest-climate.md](verification/rest-climate.md)).

### 8-4. 외부 연동

- 외부 전송: **없음.** TextToSpeech는 `ON_DEVICE`로 써서 서버로 문장을 보내지 않는다.
- API·서버·DB·계정: **필요 없음.** 인터넷 권한도 필요 없다.
- 개인정보·위치: 수집하지 않는다. FusedLocation은 쓰지 않는다.

## 9. 첫 구현 작업 [STEP 3에서 구현, STEP 3 보완에서 실제 적용·원복 실행 확인 — 결과: [verification/ambient-brightness.md](verification/ambient-brightness.md)]

**작업: 앰비언트 밝기 한 항목의 쓰기 순환 검증**

6장 쓰기 계약의 기본 순환이 에뮬레이터에서 실제로 되는지 가장 작은 단위로 확인한다.

| 단계 | 동작 | 통과 기준 / 실패 시 |
| --- | --- | --- |
| 0. 주차 확인 | 기어 `GEAR_PARK` + `isRequiresDistractionOptimization() == false` | 아니면 시작하지 않고 "주차 상태에서만 실행할 수 있어요" 표시 |
| 1. 지원 확인 | `checkAmbientLightBrightnessCapabilities` | accessType에 읽기·쓰기가 있고 대상 영역(운전석 우선)의 min/max가 있음. 아니면 쓰기 없이 종료 |
| 2. 현재값 조회 | `getAmbientLightBrightness(area)` | 값을 받음(스위치 상태도 기록). 못 받으면 쓰기 없이 종료 |
| 3. 기록 저장 | 쓰기 직전 주차 조건 재확인 → 기록 형식 버전, 작업 식별자, 영역, 원래값(2단계), 목표값(현재와 다른 범위 안 값), 처리 단계 "변경 요청 중"을 앱 내부에 저장 | 조건이 없거나 저장 실패면 쓰기 없이 종료(요청 안 함) |
| 4. 변경 | 기록 저장 직후 `setAmbientLightBrightness(area, 목표값)` | 종료 콜백(`onComplete`/`onFailed`)을 기다린다. 타임아웃이 지나도 요청은 미완료로 남고, 화면에 결과 불명(응답 대기)을 표시한다 |
| 5. 재조회 | `getAmbientLightBrightness(area)` | 종료 콜백을 받은 뒤: 목표값 → 적용 확인(Virtual Console 밝기 카드도 같은 값). `onFailed`는 재조회 값과 관계없이 결과 불명, 기록 유지(값이 바뀌지 않았다는 보장으로 보지 않음). 그 밖의 값·조회 실패 → 결과 불명, 기록 유지. **타임아웃(콜백 없음)이면 재조회 값을 표시만 하고, 원래값이어도 기록을 유지한 채 응답을 기다린다. 6단계로 가지 않는다** |
| 6. 원복 | 4단계 요청의 종료 콜백을 받았고 적용 확인 또는 부분 적용일 때만 → 쓰기 직전 주차 조건 재확인 → 처리 단계 "복원 중" 갱신 → `setAmbientLightBrightness(area, 원래값)` | 미완료 요청이 있거나 조건이 없으면 쓰지 않는다. 조건이 없으면 "복원 보류"와 원래값 표시. 주차 조건이 확인되지 않으면 원복 명령으로 넘어가지 않는다 |
| 7. 재조회 | `getAmbientLightBrightness(area)` | 원복 요청의 정상 응답(`onComplete`)을 받은 뒤: 원래값 → 복원 확인, 기록 삭제. `onFailed`면 복원 실패. 아니거나 조회 실패 → 복원 실패 또는 결과 불명, 기록 유지, 원래값과 수동 조정 방법 표시. 타임아웃이면 "복원 중"을 유지하고 응답을 기다린다 |

진행 중 주차 조건이 사라지면 이후 쓰기(3·6단계)를 보류하고 기록과 현재 상태를 화면에 표시한다. 보류된 원복은 주차 조건이 다시 확인된 뒤 사용자가 [원래대로]를 누를 때만 실행한다.

**실패 조건과 기록:** 주차 아님 / capability 없음 또는 읽기 전용 / 기록 저장 실패 / `VehicleException`의 `ERROR_SECURITY_PERMISSION`(권한 표기 문제 확인) / `onFailed` / 정해진 시간 안에 응답 없음 / 재조회 불일치·실패 / 원복 실패 / 스위치 `OFF`(변경이 눈에 보이지 않을 수 있음). 오류·타임아웃은 미변경으로 보지 않는다. 타임아웃은 요청을 끝내지 않으며, 재조회 값이 원래값이어도 응답 전에는 기록을 유지한다. 각 단계의 결과, 값, 시각, 오류를 화면 표와 로그에 남긴다.

**사용자가 확인할 결과:** 에뮬레이터 화면의 단계별 결과표. Virtual Console의 Ambient Brightness 카드 값이 바뀌었다가 원래대로 돌아오는 것.

**검증 방법:**
1. 단계 진행 로직을 가짜 Light 구현으로 단위 테스트(성공 경로, 기록 저장 실패, 타임아웃 뒤 원래값 조회 후 늦은 반영·응답(80 → 30), `onFailed` 뒤 재조회 판단, 주차 조건 상실 시 보류, 원복 실패)
2. `./gradlew :app:assembleDebug` 빌드 성공
3. 에뮬레이터 수동 확인표(입력 → 기대 → 실제)와 로그
4. Virtual Console 카드 값 대조

**착수 지시에서 승인이 필요한 것:**
- Kotlin + Compose 프로젝트 전환(현재 뼈대 `3d97a31`은 Java)
- 의존성: Pleos Maven 저장소, `ai.pleos.playground:Vehicle:2.3.2`, Kotlin·Compose 라이브러리, AAOS `android.car` 라이브러리 사용
- 권한 선언: `pleos.car.permission.CAR_LIGHTS`, `android.car.permission.CAR_POWERTRAIN`. `ERROR_SECURITY_PERMISSION`이 나면 `CONTROL_CAR_LIGHTS` 추가 비교(그때 다시 승인)
