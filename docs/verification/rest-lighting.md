# 휴식 무드등 적용·복원 검증 (STEP 8)

- 날짜: 2026-11-12 ~ 13
- 목적: 제품 휴식 흐름에서 무드등 밝기·색을 휴식 동안 바꾸고 끝나면 원래대로 돌리는 계약(제품 요구사항 6-1, 6-3, 8-3)을 실제 앱으로 확인
- 판정 기준: SDK 재조회값. `onComplete` 값은 요청 echo라 판정에 쓰지 않는다. Virtual Console·VHAL 로그는 보조 증거다.
- 결론:
  - 실제 휴식에서 무드등 적용(밝기 70→30, 색 `0xFFFF9A40` → 조회 `0x00FF9A40`)과 복원(70, `0x00FFFFFF`)을 사용자 종료·앱 이탈·정상 시간 종료·Activity 교체에서 실행 확인했다.
  - 스위치 OFF와 [무드등 조정] 끔에서는 쓰기가 0이었다.
  - 사용자 변경은 보존됐다.
  - D 전환이면 복원을 보류하고, P로 돌아와도 [원래대로] 전까지 쓰지 않았다.
  - 중간 리뷰에서 **실제 버그**를 찾았다. 새 프로세스의 첫 구독이 오래된 캐시값 70을 첫 이벤트로 보내 사용자 변경으로 오판한 것이다. 이를 고쳤고, 같은 콜드 실행 첫 휴식에서 다시 확인했다(4·5장).

### 1-1. 동작 규칙

1. 실제로 시작된 휴식에서만 적용한다. **제품 조명 컨트롤러(RestLighting)는** 준비 화면, 앱 실행, 설정 토글에서 차량을 읽거나 쓰지 않는다. [무드등 조정]이 끔이면 컨트롤러의 조회도 쓰기도 0이다(실측: 선택 끔 휴식 구간 조명 호출 0). 단, 앱 전체로는 기존 debug 밝기 진단이 `MainActivity.onCreate` 1.5초 뒤 `probe.refresh()`로 스위치·밝기를 한 번 조회한다(쓰기 없음, 이번 단계에서 바꾸지 않음).
2. 적용 순서(밝기 영역들 → 색 영역들, 한 번에 하나): capability(READ_WRITE, 영역, 밝기 범위) → 현재값과 목표 → **스위치를 마지막으로** 조회(ON만 진행) → 기록 저장(실패 = 명령 0) → 최종 확인(같은 실행, P + 주행 제한 없음, debug 없음, 저장 오류 없음, 같은 속성·영역 기록 없음) → 명령 → 종료 콜백 → 0.5초 뒤 별도 재조회로 판정.
3. 목표: 밝기 30(지원 범위로 맞추되 현재 이상이면 쓰지 않음), 색 `0xFFFF9A40`. 밝기와 색은 각자 원래값·지원·사용자 변경을 따로 관리하고, 한쪽이 실패해도 다른 쪽은 진행한다.
4. 색 계약: RGB로 비교한다. 허용 alpha는 `0x00`(실제 조회값)과 `0xFF`(문서)뿐이다. 변경·복원 요청은 모두 alpha `0xFF`이고, 원래 raw는 따로 둔다.
5. 스위치 영역 매핑: 대상 영역의 좌석을 모두 포함하는 스위치 영역이 정확히 하나일 때만 쓴다. 없거나 둘 이상이면 그 영역은 건너뛴다. 첫 영역이나 운전석을 하드코딩하지 않는다.
6. 종료: 새 준비는 즉시 취소한다. 이미 보낸 요청은 응답과 재조회를 마친 뒤 복원한다. 복원 순서: capability·원래값 재확인 → 현재값(앱 값도 원래값도 아니면 사용자 변경으로 보고 쓰지 않음) → 스위치 마지막 조회 → 기록 → 최종 확인 → 명령. 복원 확인(콜백 + 재조회 = 원래값)일 때만 기록을 지운다.
7. P 상실: 그 순간 열려 있던 작업을 기억해 두고, 복원은 보류(`RESTORE_HELD`)한다. 다시 P가 돼도 자동으로 쓰지 않고 [원래대로]로만 쓴다. 이미 보낸 복원의 늦은 확인은 계속 처리한다.
8. 잠금: 응답 없는 요청(타임아웃 포함)이 있는 기록, 이전 실행에서 응답을 못 받은 기록은 앱에서 쓰거나 복원하거나 지우지 않는다. 저장 오류 뒤에는 새 쓰기·복원·기록 추가·삭제를 하지 않는다. 손상된 파일은 그대로 두고 조명을 막는다.
9. 사용자 변경: 리스너 값만으로는 정하지 않는다. 등록 직후 서비스가 오래된 캐시값을 첫 이벤트로 보낼 수 있기 때문이다(실측: 실제 30인데 70).
   - 앱 값과 다른 값이 오면 실제 현재값을 따로 읽는다. 그 조회가 앱 값과 다를 때만 `USER_CHANGED`로 바꾸고 더 쓰지 않는다.
   - 조회가 끝나면 다음을 다시 확인하고, 하나라도 아니면 결과를 버린다: owner 유효, 같은 jobId·requestId, 단계가 그대로 적용 확인, 응답 대기·확인·복원 중이 아님.
   - 조회 중에 다른 불일치 값이 또 오면 끝난 뒤 한 번 더 읽는다. 조회가 실패하면 정하지 않는다.
   - 첫 이벤트를 무조건 버리지 않고, 밝기·색에 같은 규칙을 쓴다. 종료 직전 조회도 같은 기준이다.
   - 꺼진 스위치를 켜거나 꺼진 무드등에 색·밝기를 쓰지 않는다.
10. 수명: owner는 프로세스 단위다. Activity의 `onStop`/`onDestroy`(Activity Handler 정리, Activity의 `Vehicle.release()`)는 owner를 끊지 않는다. RestFlow 세션 번호는 Activity마다 1부터 다시 시작하므로, 시작·종료는 owner가 발급한 실행 번호로 잇는다. 이전 Activity의 늦은 종료는 번호가 달라 무시된다. 프로세스가 강제로 끝나면 복원 완료는 보장하지 않는다(기록이 남아 다음 실행에 안내).
11. debug 상호 배제: 제품 조명이 준비·응답 대기·복원 중이거나 기록이 있으면 debug 밝기/제어 도구는 차량 쓰기를 거부한다. 반대로 debug 작업 중이거나 debug 기록(손상 포함)이 있으면 제품은 적용과 [원래대로]를 하지 않고 이유를 보여 준다.

### 1-2. 기록 형식

`{"formatVersion":1,"records":[{jobId, prop(BRIGHTNESS|COLOR), area, original, target, stage, requestId, payload, responseReceived, priorRequestUnresolved, lastEcho, lastRead}]}`

- 밝기 값은 JSON 정수, 색 값은 `"0xAARRGGBB"` 문자열이다.
- 엄격 검사: 버전, 이름, 영역, 밝기 target < original, 색 target = `0xFFFF9A40`, payload alpha `0xFF`, original alpha `00`/`FF`를 확인한다. 같은 속성·영역, jobId, requestId가 둘 이상이면 손상으로 본다.
- STEP 3 밝기 v1 기록(`ambient-probe-recovery.json`)과 STEP 7 bench 기록(`vehicle-control-records.json`)은 읽기만 하고(차단 판단용) 바꾸지 않는다.
- 설정: SharedPreferences `comma_cabin_rest`에 `rest_lighting`(참/거짓)을 더했다. 기존 `onboarding_version`·`rest_sound`·`rest_level`은 그대로다. 버전 2 사용자는 무드등 문장이 든 안내를 한 번 다시 본다.

## 7. 한계와 미실행

1. 실제 SDK `onFailed`, 쓰기 타임아웃, 늦은 응답은 에뮬레이터에서 만들 수 없어 단위 테스트로만 확인했다. 모든 실기 요청은 0.01~0.05초 안에 `onComplete`로 끝났다.
2. 저장 실패·손상 기록·이전 실행 미응답 기록·debug 기록과의 상호 배제는 단위 테스트로만 확인했다(앱 데이터를 지우거나 파일을 조작하지 않음).
3. 휴식 중 사용자 변경은 정상 차량 UI 오버레이가 없어 Console 보이는 밝기 카드와 같은 요청을 직접 보낸 fixture로 만들었다. 실제 화면 조작으로 바꾼 것이 아니다.
4. 프로세스 강제 종료 뒤의 다음 실행 안내(새 프로세스에서 기록 카드)는 실기로 만들지 않았다. 기록 파일 유지와 잠금 규칙은 단위 테스트로 확인했다.
5. 오래된 색 이벤트는 실기에서 재현되지 않았다(단위 테스트로 확인).
