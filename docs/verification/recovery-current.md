# 다음 실행의 남은 기록: 차량 설정 확인 표시 (STEP 11)

- 날짜: 2026-11-13
- 목적: 제품 요구사항 6-1·6-6·F15는 다음 실행 때 남은 기록을 보여 주고, 차량 설정을 쓰기 없이 읽으라고 한다. 이전 구현은 기록만 불러오고, 실제 값은 [원래대로]를 누를 때 처음 읽었다. 이 누락을 채운다(STEP 9 리뷰에서 놓친 부분이며, 요구사항은 바꾸지 않았다).
- 바꾸지 않은 것: 쓰기·복원 알고리즘, 포트의 쓰기 계약, 기록 파일명·형식 버전·원래값·목표값·응답 표시·요청 ID·단계·잠금, 시트(움직이지 않음), 화면 꺼짐 처리(STEP 10의 onStop 그대로).
- 판정 기준: 차량 값은 SDK 재조회값으로 판정한다. Console 값은 보조 증거다.

## 1. 구현

**언제 읽는가**
- 남은 기록이 있을 때만 읽는다. 기록이 없으면 이 기능은 SDK를 부르지 않는다.
- 화면이 보일 때 한 번 읽는다. Activity `onStart` 뒤 1.5초에 실행한다(SDK 연결 대기, 기존 진단과 같은 지연).
- [다시 확인]을 누르면 다시 읽는다.
- 상시 폴링은 하지 않는다. 무드등·공조 작업(적용·응답 대기·복원)이 진행 중이면 읽지 않는다.

**무엇을 읽는가**: 기존 공개 읽기 API만 쓰고, 기록에 저장된 항목·영역 그대로 읽는다(영역을 추측하지 않는다).
- 무드등: 기록된 영역의 밝기 또는 색.
- 공조: 기록된 풍량·운전석 온도, 그리고 그룹의 전원·자동·연동(Sync) 상태.

**어떻게 보여 주는가**: 기록 카드의 항목마다 원래값(기록) 아래에 "확인한 …"으로 보여 준다.
- 비교 결과는 "원래와 같아요", "휴식 목표와 같아요", "원래와 달라요" 중 하나다. 색은 "원래 색과 같아요", "휴식 목표 색과 같아요", "원래 색과도 휴식 색과도 달라요" 중 하나다.
- 목표값과 같다는 사실만으로 이전 요청이 적용됐다고 말하지 않는다. 미응답 기록에서도 비교 사실만 보여 준다.
- alpha가 00·FF가 아닌 색은 비교하지 않고 "색을 읽었지만 비교할 수 없는 값이에요"로 보여 준다(STEP 8 색 계약).
- 읽지 못하거나 시간이 초과되면 "차량 설정을 확인하지 못했어요"로 보여 주고, [다시 확인]으로 다시 읽을 수 있다.
- 조회 중에는 "차량 설정을 확인하고 있어요"를 보여 준다.
- 실패했을 때 목표값이나 이전 `lastRead`로 대신 채우지 않는다. 새로 조회할 때마다 이전 결과를 지운다.
- 카드 문구는 "확인한 설정은 확인한 순간의 값이에요. [원래대로]는 누를 때 다시 확인해요."다. 읽은 값을 "현재값"이라고 보장하지 않는다.
- 화면에 SDK 키·예외·작업 ID는 나오지 않고, 기술 내용은 로그에만 남긴다.

**쓰기·기록 영향**: 없다.
- 조회 결과는 메모리 표시용(controller 안의 맵)이다.
- 차량 명령, 자동 복원·재시도, 기록 추가·수정·삭제, 요청 종료 판정, 잠금 해제를 일으키지 않는다.
- 미응답 기록은 값이 원래와 같아도 [원래대로]·[기록 지우기]가 계속 막혀 있다.
- [원래대로]는 기존처럼 쓰기 직전에 다시 조회하고 조건을 검사한다.

**늦은 응답 방어**
- 결과는 조회 세대가 같을 때만 받는다. 세대는 새 휴식, 복원 시작(자동·명시), 기록 삭제, owner close, 그 화면의 숨김 때 바뀐다.
- 조회의 각 단계와 결과를 받을 때마다 최신 기록과 대조한다(같은 요청 ID·단계·응답 표시). 바뀌거나 지워진 기록은 결과를 넣지 않고 건너뛴다.
- 화면에 보여 줄 때도 같은 기록일 때만 보여 준다.
- 세대가 바뀌면 "확인하고 있어요" 표시가 끝나고, 다시 확인할 수 있다.

**화면 교체 순서**
- 조회는 시작한 화면(Activity)을 owner로 기억한다. 새 Activity가 조회를 요청하면 이전 조회를 무효로 하고 새 조회를 시작한다.
- 늦게 오는 이전 Activity의 `onStop`은 자기 owner의 조회만 멈출 수 있어서, 새 화면의 조회를 지우지 못한다.
- 조회를 멈출 때 Handler 전체를 비우거나, 차량 적용·복원·응답 대기 타이머를 취소하지 않는다. 읽기 시간 초과 타이머는 그대로 끝나고, 결과는 세대가 달라 버려진다.

**바뀐 파일**:
- `lighting/RestLighting.kt`·`climate/RestClimate.kt`: `checkRecords(owner)`, `stopCheck(owner)`, 표시 필드 `checked`와 `checking`.
- `MainActivity.kt`: `onStart` 뒤 조회, `onStop`에서 자기 조회만 멈춤, [다시 확인] 연결.
- `RestScreen.kt`: 확인한 값 줄, 안내 문구, [다시 확인] 버튼.
- 테스트.

## 5. 단위 테스트(새로 추가한 것)

- `RestClimateTest`:
  - 다음 실행에서 영역별로 확인한 값을 표시한다. 차량 명령·기록 변경·자동 복원은 0이고, 외부 변경으로 단정하지 않는다.
  - 기록이 없으면 호출 0이다. 미응답 기록은 원래값을 읽어도 잠금이 유지된다.

  - 늦은 응답이 오래된 화면의 늦은 정지, 복원, 새 휴식, 삭제, owner 교체를 오염시키지 않는다. 무효가 된 뒤 다시 확인할 수 있다.
- `RestLightingTest`:
  - 밝기·색을 확인한 값으로 표시한다. 쓰기·기록 변경 0이고, 기록이 없으면 호출 0이다. 해석할 수 없는 색 형식은 비교하지 않는다.
  - 오래된 화면의 늦은 정지가 새 조회를 지우지 않는다. 새 휴식 뒤 늦은 응답은 버린다. 미응답 기록은 잠금이 유지된다.

## 6. 표시의 한계와 실행하지 않은 것

- 확인한 값은 읽은 순간의 값이다. 그 뒤 차량에서 바뀔 수 있다.
- 실제 미응답 기록은 만들지 않았다. 중간 요청을 끊거나 파일을 조작하지 않았다. 미응답 잠금 유지는 단위 테스트로만 확인했다.
- 실기로 확인하지 않고 단위 테스트로만 확인한 것: 조회 실패·시간 초과, 늦은 응답, Activity 교체 순서(새 화면 시작 뒤 이전 화면 정지), 해석할 수 없는 색 형식.
- "다시 보이는 화면" 경로는 실기에서 새 프로세스 실행만 확인했다. 다른 앱으로 갔다가 돌아오는 경우는 실기로 확인하지 않았다(코드상 `onStart`에서 같은 조회를 한다).
- 무드등은 밝기만 바꾼 상태를 실기로 확인했다. 색만 다른 경우는 실기로 확인하지 않았다.
